# 项目需求确认

## 1. 项目目标

开发一个可在手机端运行的相机应用，用户可以导入 2D 图片角色或 3D 模型角色，与角色一起进行自拍，形成“突破次元壁”的合影体验。

该产品的核心体验不是传统拍照工具，而是“虚拟角色陪伴式自拍相机”。

## 2. 当前确认的核心诉求

基于当前描述，需求可以整理为以下几个核心点：

1. 应用需要在手机端运行。
2. 用户可以导入自己的角色资产：
   - 2D 图片，例如 OC 立绘、Q 版角色图。
   - 3D 模型，例如 GLB/GLTF 格式角色。
3. 应用需要支持前置摄像头自拍。
4. 导入的角色需要出现在相机画面中，与真人同框。
5. 角色需要具备一定“意识感”，至少表现为：
   - 看向镜头或看向用户。
   - 有轻微待机动作。
   - 拍照时能做出回应。
6. 最终需要输出合影照片。

## 3. 产品愿景

让用户可以把自己创作的 OC、喜欢的 Q 版角色、或收藏的虚拟形象带入现实自拍场景，获得一种轻量、浪漫、可分享的虚实合影体验。

## 4. 目标用户

1. 喜欢原创角色创作的用户。
2. 喜欢乙游、二次元、Q 版角色陪伴感的用户。
3. 有角色展示、社交分享、头像创作需求的用户。
4. 想快速做“我和角色合影”内容的移动端用户。

## 5. 核心使用流程

1. 用户打开应用。
2. 选择前置摄像头。
3. 导入一个 2D 图片或 3D 模型。
4. 调整角色的位置、大小、朝向。
5. 角色在相机中进行轻微互动或待机动作。
6. 用户点击快门进行自拍。
7. 系统导出合影结果。

## 6. 范围划分

## 必做范围（MVP）

1. 手机浏览器可访问。
2. 支持前置摄像头预览。
3. 支持导入 2D 图片。
4. 支持导入 3D 模型（优先 GLB）。
5. 支持拖拽、缩放、旋转角色。
6. 支持拍照并导出成图。
7. 角色具备基础“活着”的感觉：
   - 呼吸浮动
   - 轻微摆动
   - 朝向镜头

## 暂不纳入 MVP 的能力

1. 多角色同屏。
2. 复杂骨骼驱动动画编辑器。
3. 云端角色资产库。
4. AI 实时对话。
5. 高精度 AR 空间锚定。
6. 复杂美颜和滤镜系统。

## 7. 对“角色有意识”的产品定义

为了避免范围失控，第一阶段将“意识感”定义为可感知的实时反馈，而不是完整 AI 人格系统。

第一阶段包含：

1. 视线朝向镜头或用户面部区域。
2. 待机动作循环。
3. 拍照前后做简单回应动作。
4. 可选的表情切换或气泡反馈。

后续阶段再考虑：

1. 语音回应。
2. 文本互动。
3. 情绪状态机。
4. 基于场景的主动动作。

## 8. 资产格式建议

### 2D

1. PNG 透明底优先。
2. JPG 作为兼容格式。

### 3D

1. GLB 作为首选格式。
2. GLTF 作为兼容格式。
3. 后续再评估 VRM 支持，以适配更完整的角色生态。

## 9. 关键非功能需求

1. 手机端操作简单，单手可完成主要流程。
2. 首屏进入拍摄页，不做重营销首页。
3. 角色渲染在中端手机上保持基本流畅。
4. 本地导入、本地渲染优先，降低服务端依赖。
5. UI 以相机工作流为中心，减少复杂配置。

## 10. 当前默认假设

以下假设用于启动第一轮产品设计，如与你预期不一致，下一轮可直接调整：

1. 第一版优先做 Web App / PWA，而不是原生 iOS / Android 双端。
2. 第一版重点验证“自拍合影体验”，不是角色养成。
3. 第一版默认单角色导入。
4. 第一版优先本地文件导入，不接在线模型市场。
5. 第一版先做照片输出，再考虑视频录制。

## 11. 当前阶段验证重点

当前阶段的目标，已从“先补齐所有自拍闭环细节”调整为“先做出可对外展示并能拿到反馈的互动效果 demo”。

1. 优先验证角色是否能在镜头中体现空间感、陪伴感和互动感。
2. 优先支持真机录屏或演示拍摄，而不是先把应用内视频录制做成正式功能。
3. 除非是会影响后续架构的大项，否则保存、分享、成片一致性等稳定性问题可以后置。
4. 为了支撑更自然的互动表现，允许在效果验证前先补入带骨骼角色与默认待机动画的接入能力。
