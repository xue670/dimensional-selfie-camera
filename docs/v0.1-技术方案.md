# V0.1 技术方案

## 1. 技术目标

以最低实现成本快速验证“手机端虚拟角色自拍”体验是否成立，同时保留后续升级到更强互动和资产生态的空间。

补充说明：

1. 当前技术目标已扩展为两条并行主线：
   - 保持基础自拍链路可用
   - 提前接入带骨骼角色的默认动画能力，为互动版本铺路
2. 因此 `V0.1` 不再只关注静态模型显示，而是要求 3D 层具备“动画可识别、可播放、可回退”的基础结构。

## 2. 技术选型

## 前端框架

1. React + Vite
2. TypeScript

选择原因：

1. 启动快，适合原型迭代。
2. 组件化便于后续增加拍照流程、资产面板和角色控制。
3. TypeScript 有利于约束资产和渲染状态。

## 渲染层

1. 2D 角色：HTML/CSS + Canvas 或绝对定位图层
2. 3D 角色：Three.js

选择原因：

1. 2D 和相机 UI 的组合用 DOM 层更直接。
2. 3D 模型导入、灯光、动画控制适合 Three.js。

## 相机能力

1. `navigator.mediaDevices.getUserMedia`

选择原因：

1. 浏览器原生能力，适合移动端 Web 原型。
2. 可直接接前置摄像头视频流。

## 拍照合成

1. 使用离屏 Canvas 合成：
   - 视频帧
   - 2D 角色层
   - 3D 渲染层

选择原因：

1. 便于导出单张图片。
2. 后续可以扩展滤镜与贴纸层。
3. 便于对“保存图片”和“系统分享”做能力分级。

## 3. 系统结构

建议采用以下模块：

1. `camera`
   - 管理摄像头权限、流、前后置切换
2. `asset-loader`
   - 加载 2D 图片与 3D 模型
3. `scene-controller`
   - 管理角色位置、缩放、旋转、动画状态
4. `renderer`
   - 负责 2D/3D 可视呈现
5. `capture`
   - 负责截图合成与导出
6. `ui`
   - 快门、导入、重置、模式切换等控制

## 4. 页面结构建议

V0.1 建议采用单页结构：

1. 全屏相机预览层
2. 角色叠加层
3. 顶部轻量状态栏
4. 底部操作栏：
   - 导入
   - 模式提示
   - 快门
   - 重置

## 5. 核心实现思路

## 相机层

1. 用 `video` 元素承载摄像头流。
2. 设置 `playsInline`、`muted`、`autoplay`。
3. 优先请求 `facingMode: user`。
4. 相机流 ready 后再开放拍照按钮，避免空白帧导出。

## 2D 角色

1. 以透明 PNG 作为独立覆盖层。
2. V0.1 以 PNG 为强制支持格式，JPG 作为兼容增强项。
3. 通过触控事件实现拖拽和缩放。
4. 用 CSS 动画或 `requestAnimationFrame` 实现呼吸浮动。

## 3D 角色

1. 使用 Three.js 加载 GLB。
2. 渲染在透明背景 Canvas 上。
3. 模型容器支持整体平移、缩放、旋转。
4. 若模型自带骨骼动画，优先识别并播放一条默认待机动作。
5. 默认动作名优先匹配 `idle / breath / stand / wait / loop` 等关键字；若未命中，则回退到第一条 clip。
6. 若无动画，则给模型根节点增加轻微摆动，作为轻量待机回退。
7. 导入后对模型做包围盒计算，执行自动居中、默认缩放和朝向校正。
8. V0.1 中 GLB 为强制支持格式，GLTF 延后。
9. 当前阶段不引入复杂动作编辑器，但需要保留“后续互动事件 -> 动画播放”挂接点。

## 动画接入策略

1. 使用 `THREE.AnimationMixer` 管理带骨骼模型的动作播放。
2. 一个模型在导入后至少维护：
   - 当前可用 clip 列表
   - 当前激活动作
   - 是否启用回退待机
3. 首轮只要求默认待机动画自动播放，不要求复杂的多动作状态机。
4. 进入当前 `V0.2` 阶段后，已经补上一个最小互动状态机：
   - `idle -> response -> idle`
5. 当前实现里，响应动作结束后应通过 `crossFade` 平滑回到 `idle`，避免先 `stop()` 再切回导致瞬间出现不属于任何动作的怪姿势。
6. 后续互动版本可在当前基础上继续扩展为：
   - `idle`
   - `response`
   - `triggered`
   - `recover`

### 资产侧补充约束

1. `response` 的首帧尽量贴近 `idle`，减少切入时突兀感。
2. `response` 的尾帧也尽量回到接近 `idle` 的姿势，减少回切时断层。
3. 如果 `response` 首尾与 `idle` 差异很大，即使代码做了淡入淡出，仍可能出现手臂、脖子或嘴部突然抽动。

## 拍照合成

1. 将视频当前帧绘制到离屏 Canvas。
2. 将 2D 角色层绘制到同一 Canvas。
3. 将 Three.js Canvas 覆盖绘制到最终 Canvas。
4. 导出为 PNG。
5. 保存能力作为 V0.1 必选项，系统分享通过 Web Share API 做可用即启用、不可用即回退保存。

## 7. 兼容性与风险

## 风险 1：移动端浏览器相机权限限制

应对：

1. 本地开发时使用局域网或 HTTPS。
2. 生产部署必须启用 HTTPS。
3. 首次授权耗时不纳入页面冷启动性能指标。

## 风险 2：3D 模型规格不统一

应对：

1. V0.1 只保证 GLB 优先可用。
2. 增加模型加载失败提示。
3. 自动居中和自动缩放到默认视野。
4. 增加默认朝向校正，避免角色背对镜头。
5. 带动画模型先采用“识别默认待机动作 + 第一条 clip 回退”的宽松策略，降低资产命名差异带来的失败概率。

## 风险 3：拍照合成跨层截图复杂

应对：

1. 从一开始就采用视频层 + 透明 3D Canvas + 可控 2D 层的结构。
2. 避免依赖直接对 DOM 截屏的方案。

## 风险 4：触控手势冲突

应对：

1. V0.1 优先支持单指拖动、双指缩放。
2. 旋转操作可以先做成按钮或滑杆辅助。

## 风险 5：移动端系统分享兼容性不一致

应对：

1. V0.1 先保证图片保存成功。
2. 检测 `navigator.share` 和 `navigator.canShare`。
3. 不支持系统分享时自动回退到下载/保存流程。

## 风险 6：带骨骼 GLB 动画命名与导出不一致

应对：

1. 不强依赖 clip 名必须叫 `idle`。
2. 先匹配常见待机关键字，再回退到第一条可用 clip。
3. 在 UI 中提示当前正在播放的动作名，方便快速判断是代码问题还是资产导出问题。
4. 无动画或动画识别失败时，仍保留轻量待机，不让模型完全静止。
5. 若 `response` 首尾姿势与 `idle` 差异过大，应优先回到 Blender 对齐首尾帧，而不是只依赖前端混合时间硬扛。

## 9. 里程碑建议

1. 先搭相机预览。
2. 再接 2D 角色导入与摆放。
3. 再接 3D 模型导入与透明渲染层。
4. 完成截图合成与保存。
5. 补齐带骨骼 GLB 的默认待机动画接入。
6. 最后再把互动触发挂到动画播放能力上。

## 10. 下一步实施建议

当前建议不再是工程初始化，而是进入分版本推进：

1. 先完成 `V0.1.3` 中不阻断互动演示的必要收口。
2. 进入 `V0.1.4`，验证带骨骼 `GLB` 能识别并播放默认待机动作。
3. 再进入 `V0.2`，实现固定陪伴位、空间感和第一批互动触发。
